# バンドセッション予約システム UI設計書

---

## 🎯 目的

バンドセッションへの参加者が、演奏したい曲・担当パート・希望日程をスムーズにオンライン予約できる Web アプリ。
音楽系サービスらしいダークでモダンな UI により、参加者がセッションへの期待感を高めながら操作できる体験を目指す。

## 👤 ユーザー

バンドセッションに参加したい一般ユーザー（楽器演奏者・ボーカリスト）。

## 🧩 機能一覧

- トップページ（開催予定イベント一覧・過去イベント・予約への導線）
- 予約フォーム（名前・日付・曲名・パート・コメントの入力と送信）
- クライアントサイドバリデーション（リアルタイムエラー表示）
- 送信フィードバック（成功・失敗メッセージ）

## 2. ユーザー導線

### メインフロー（予約完了まで）

```
① トップページ（/）にアクセス
        │
        │  ヒーローセクションを確認
        │  開催予定イベント一覧を確認
        │
        ├─ 「詳細を見る」クリック → 詳細モーダル表示
        │       │
        │       └─ モーダル内「予約する →」クリック
        │
        └─ イベントカードの「予約する」クリック
                │
                ▼
② 予約フォームページ（/reserve?eventId=xxx）
        │
        │  ページ上部でイベント情報を確認
        │  「詳細を見る」で詳細モーダルを再確認（任意）
        │  名前・曲名・パートを入力（日付は自動セット）
        │  コメントを任意で入力
        │
        ▼
③ 「予約を送信する」ボタンをクリック
        │
        ├─ バリデーションエラー → エラー表示 → ② に戻る
        │
        └─ 送信成功 → 成功メッセージ表示・フォームリセット
```

### サブフロー

- 予約フォームページから「← トップへ戻る」でトップに戻れる
- `eventId` なしで `/reserve` にアクセスした場合はトップへリダイレクト

| h1 | 「セッション予約」 | フォントウェイト 800 |

| パートフィールド | セレクトボックス | カスタム矢印アイコン付き |
| コメントフィールド | テキストエリア（3行） | 「任意入力です」ヒントテキスト付き |
| 送信ボタン | 「予約を送信する →」 | 幅100%、送信中はスピナー＋「送信中...」に変化 |

#### UX 設計

- **イベントサマリー**：フォーム上部に対象イベントを明示し、「どのイベントに予約しているか」を常に確認できる
- **日付の自動セット**：イベント日付を読み取り専用で表示し、誤入力を防ぐ
- **必須マーク**：ラベル末尾に `*`（アクセントカラー）を付与し、必須フィールドを一目で識別
- **エラー表示**：フィールド直下にインラインで表示
- **エラーの自動クリア**：入力を再開した時点でそのフィールドのエラーが消える
- **二重送信防止**：送信中はボタンを `disabled` + スピナー表示にして誤操作を防ぐ
- **成功時のフォームリセット**：送信成功後にフォームを初期化し、連続予約の操作を妨げない

## 5. 状態管理の設計

### グローバルに持つべき状態

現バージョンでは**グローバル状態なし**。Context / Zustand 等は不要。

### 各画面の状態

#### トップページ（`/`）

| 状態 | 管理コンポーネント | 型 | 用途 |
|---|---|---|---|
| モーダル表示中のイベント | `EventModal` | `Event \| null` | どのイベントの詳細を表示するか |
| 過去イベント展開状態 | `PastEventsAccordion` | `boolean` | アコーディオンの開閉 |

#### 予約フォームページ（`/reserve?eventId=xxx`）

状態はすべて `ReserveForm` コンポーネント内の `useState` で管理。

| 状態 | 型 | 初期値 | 用途 |
|---|---|---|---|
| `form` | `ReservationForm` | 全フィールド空文字 / `part: "guitar"` | 各入力フィールドの値 |
| `errors` | `FormErrors` | `{}` | フィールドごとのバリデーションエラー文字列 |
| `isSubmitting` | `boolean` | `false` | 送信中の UI ロック・スピナー表示 |
| `result` | `ApiResponse \| null` | `null` | 送信結果のアラートバナー表示 |

### フォーム状態の遷移

```
初期状態（空フォーム）
    │ 入力
    ▼
入力中（errors は入力のたびにクリア）
    │ 送信ボタンをクリック
    ▼
バリデーション実行
    ├─ NG：errors にメッセージをセット → 入力中に戻る
    └─ OK：isSubmitting = true
                │ API 通信
                ├─ 成功：result = {success: true}、form をリセット、isSubmitting = false
                └─ 失敗：result = {success: false}、isSubmitting = false
```

## 6. レスポンシブ設計

### ブレークポイント方針

明示的なブレークポイント定義はなく、`max-width: 640px` の中央揃えコンテナと `auto-fit` グリッドにより自然にレスポンシブ対応。

### レイアウト差分

| 要素 | モバイル（〜480px） | タブレット（481〜768px） | PC（769px〜） |
|---|---|---|---|
| コンテナ幅 | 画面幅 − 余白（padding: 0 1.5rem） | 画面幅 − 余白 | 最大 640px（中央揃え） |
| 特徴カード | 1列（縦並び） | 2列または3列（auto-fit） | 3列 |
| フォームカード | 画面幅いっぱい | 画面幅いっぱい | 最大 640px |
| h1 フォントサイズ | `clamp` により小さく（最小 2rem） | 中間サイズ | 最大 3.25rem |
| 送信ボタン | 幅100%（full-width） | 幅100% | 幅100% |

### モバイル固有の考慮点

- `type="date"` ピッカーはネイティブ UI（OS 依存）を使用。iOS Safari でも `min` 属性による過去日制限は機能する
- セレクトボックスはネイティブ UI のため、モバイルでは OS 標準のドラムロールピッカーで選択される
- タップターゲットはパディングにより十分な高さを確保（各入力フィールド約 44px 相当）

## 7. UI/UX 改善ポイント

### 現状の課題と改善提案

---

#### 改善① 送信成功後のフィードバックが弱い

**現状**：フォームの上部にアラートバナーを表示してフォームをリセットするのみ。

**課題**：フォームリセット後にバナーが残り、どの内容で予約されたか確認できない。

**提案A**：成功時に「予約確認カード」（名前・日付・曲名・パートのサマリー）をフォームと入れ替えて表示し、予約内容を視覚的に確認させる。
**提案B**：成功後に専用の完了ページ（`/reserve/complete`）へリダイレクトする。

---

#### 改善② パート選択がセレクトボックス1択

**現状**：セレクトボックスのみ。

**課題**：音楽系サービスの雰囲気に対して無機質。パート数が少ない（6種）ため選びにくい理由はない。

**提案**：アイコン付きのトグルボタン群（Button Group）に変更。視覚的に選んでいる感が出て、サービスの世界観にも合う。

```
[ 🎸 ギター ]  [ 🎵 ベース ]  [ 🥁 ドラム ]
[ 🎹 キーボード ]  [ 🎤 ボーカル ]  [ ➕ その他 ]
```

---

#### 改善③ フォームの進捗が見えない

**現状**：すべての項目が一画面に並んでいる。

**課題**：入力必須項目が4つあり、初見ユーザーに「全部入力しなければならない」というプレッシャーを与える可能性がある。

**提案**：各フィールドの入力が完了するごとにラベル横にチェックマーク（✓）をインジケーターとして表示し、残り項目を意識させる。（ステッパー UI は現規模では過剰のため非推奨）

---

#### 改善④ 日付フィールドの UX

**現状**：ブラウザ標準の `input[type="date"]` を使用。

**課題**：表示フォーマットがブラウザ・OS 依存。日本語環境では `年/月/日` 形式だが、英語 OS では `MM/DD/YYYY` になる。

**提案**：`min` 属性によるデフォルトの制限を維持しつつ、入力欄の下に「例：2026-04-01」形式のヒントを追加し、フォーマットの混乱を防ぐ。

---

#### 改善⑤ ヘッダーナビのアクティブ状態

**現状**：ヘッダーの「予約する」リンクは常にミュートカラーのまま。

**提案**：`/reserve` ページでは「予約する」をアクセントカラーで強調し、現在地をナビゲーションで示す。

---

#### 改善⑥ コメント欄の位置

**現状**：コメント欄はフォームの最下部、送信ボタンの直前に配置。

**課題**：任意項目と必須項目が混在しているため、ユーザーが「コメントも書かないといけない？」と迷う可能性がある。

**提案**：コメント欄のラベルを「コメント（任意）」と明記した上で、ヒントテキストと共にフォームカード内で視覚的に区切り線を引いて任意エリアを分離する。
